## INV-6.1 — registro existente para pantallas autorizadas

Resultado: **REUSE**.

Registro recomendado: `lf_ops.reglas`, usando `valor_config` con una regla dedicada.

Evidencia:
- `lf_ops.reglas` ya es un registro gobernado de configuración/reglas.
- Existen reglas con conjuntos de pantallas; por ejemplo `B2B-RULE-AUTH-046` usa `valor_config.screen_ids = [51,52,53,54,56]`.
- `INPUT_READINESS_CONTRACT` ya declara `canonical_universe_rule = B2B-RULE-STORY-READINESS-001` y `family_universe_source = lf_ops.reglas.valor_config.families`, por lo que Input Governance ya reconoce `lf_ops.reglas` como fuente de configuración canónica.

No reutilizar:
- `B2B-RULE-AUTH-046`: semántica distinta; solo prueba que el registro soporta conjuntos de pantallas.
- `public.lf_operation_registry`: modela operaciones/capacidades y no tiene payload JSON de configuración.
- `programacion.contratos`: modela contrato de ejecución; meter allí el allowlist operativo mezclaría contrato con configuración gobernada.
- `lf_activos`: inventario/registro de activos, no autoridad de configuración.

Salida para INV-6.2:
- reutilizar la tabla `lf_ops.reglas`;
- crear una regla dedicada para el allowlist de recuración, no una tabla/registro nuevo;
- sugerencia de código: `INPUT-GOV-RECURATION-AUTHORIZED-SCREENS-001`;
- payload mínimo futuro: `{"screen_ids":[1,2,3,5,43,51,52,53,54,55,56,57,58],"scope":"N2"}`;
- 6.2 debe ser Git-first y cerrar Git = ledger = BD. No se crea nada en este diagnóstico.
